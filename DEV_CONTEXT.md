## 2. Архитектурные требования и целевой стек

### 2.1. Протокол и транспорт (Inbound)
- **Протокол**: `VLESS` + `Reality`
- **Транспорт**: `xHTTP` (SplitHTTP / HTTP/2-HTTP/3 chunking)
- **Режим транспорта**: `packet-up` (дробление трафика на мелкие псевдо-REST запросы для преодоления DPI/ТСПУ поведенческого анализа).
- **План по маскировке (SNI / Reality)**:
  - Выбор из пула проверенных зарубежных CDN с поддержкой TLS 1.3 + HTTP/2 (ALPN `h2,http/1.1`), не входящих в черные списки РКН и не перенаправляющих на РФ-IP.

### 2.2. Маршрутизация и выходной узел (Outbound)
- **IPv4 Only**: `domainStrategy: "UseIPv4"` в outbound `freedom` для исключения кривой гео-локации.
- **WARP-интеграция**: Cloudflare WARP настраивается нативным Wireguard outbound в самом ядре Xray (через ключи, полученные по API).
- **Blackhole (Защита от скана)**: Блокировка попыток выхода на домены и IP зоны РФ.

### 2.3. Вспомогательные утилиты управления (CLI / TUI)
*Первоначальный план был создавать отдельные команды типа rmuser, sharelink и т.д., но в финальной архитектуре от них отказались в пользу единого интерактивного пульта (TUI).*

- `/usr/local/bin/xray_menu` — Главный TUI-пульт, точка входа.
- `/usr/local/bin/userlist` — Интерактивный список клиентов. При выборе клиента открывается карточка управления (показ QR, вкл/выкл WARP, удаление).
- `/usr/local/bin/newuser` — Мастер создания клиента (SNI, UUID).
- `/usr/local/bin/show_problems` — Дашборд здоровья и парсинг логов инцидентов.
- `/usr/local/bin/xray_update_geoip` — Скрипт обновления баз из GitHub.
- `/usr/local/bin/xray_upgrade` — Скрипт аудита и обновления (Ядро, Скрипты, Базы).
- `/usr/local/bin/xray_help` — Справочник.

- Сформирована концепция отказа от чистого TCP Reality в пользу `xHTTP (packet-up)`.

### [2026-09-11] Эволюция UX и создание TUI
- **Отказ от зоопарка скриптов**: Принято решение не заставлять пользователя учить 10 команд. Создано единое графическое (в консоли) меню `xray_menu`.
- **Инкапсуляция логики**: Удаление и генерация ссылок теперь часть `userlist`.
- **Защита целостности**: Добавлен тест конфигурации `xray -test` в скрипты генерации пользователей.
- **Горячие исправления (Hotfixes)**: Убраны конфликты симлинков, исправлена валидация пользовательского ввода в bash, улучшен лог в консоли при апгрейдах.

### [2026-09-12] Стабилизация Cloudflare WARP и Интеграция API
- **Ретраи API Cloudflare**: API регистрации `api.cloudflareclient.com` часто выдает таймауты или отказывает при первом обращении. Реализован цикл на 3 попытки с задержкой, что полностью решило проблему "пропавшего" канала WARP при чистой установке.
- **Динамические ключи Cloudflare**: Публичный ключ пира (Peer Public Key) и IP-адрес эндпоинта (Endpoint) **НЕЛЬЗЯ хардкодить** (`bmXOC...` и `162.159.192.1`). Cloudflare выдает уникальные ключи и эндпоинты в зависимости от региона/аккаунта при регистрации. Их необходимо парсить динамически из ответа API (`peers[0].public_key` и `peers[0].endpoint.host`).
- **Баг Kernel TUN в Xray**: По умолчанию Xray пытается использовать ядерный модуль Wireguard. На многих VPS и в контейнерах это приводит к ошибке `failed to create virtual tun interface > invalid argument` из-за нехватки прав. **Обязательно** добавлять параметр `"kernelMode": false` в настройки wireguard outbound.
- **Умная миграция (`xray_migrate`)**: Добавлена логика "самолечения" конфигов. Если скрипт видит, что исходящий канал `warp` отсутствует или в нем не хватает `kernelMode`, он автоматически запрашивает новые ключи у Cloudflare и бесшовно патчит `config.json` на лету.

## 4. Технические инсайты и ловушки (Gotchas)
> Этот раздел обязателен к прочтению агентом перед любыми изменениями кода!

1. **Wireguard Outbound в Xray**:
   - ВСЕГДА используйте `"kernelMode": false` в `settings`. Иначе на многих хостингах трафик будет тихо дропаться.
   - Обязательно наличие `"mtu": 1280`.
   - Требуется корректный парсинг `reserved` байтов из `client_id` (базовый массив `[0,0,0]` или декодированный base64).
2. **Cloudflare WARP API**:
   - При регистрации обязательно оборачивать запрос в цикл (до 3 раз, `sleep 3`).
   - Ответ API (`WARP_RESP`) должен парситься с помощью `jq` для извлечения IPv4/IPv6, `client_id`, `peers[0].public_key` и `peers[0].endpoint.host`.
3. **Обновления конфигов (jq)**:
   - Не используйте подстановку bash-переменных напрямую внутрь строки-кода `jq` (т.е. `jq '... \${VAR} ...'`). Всегда используйте `--arg varname "$VAR"` (для строк) и `--argjson varname "$VAR"` (для массивов/объектов), чтобы избежать инъекций и ошибок парсинга.
4. **Маршрутизация пользователей**:
   - Индивидуальная маршрутизация через WARP работает через правило роутинга `{"type": "field", "outboundTag": "warp", "user": ["USERNAME"]}`. Если канала `warp` физически нет в массиве `outbounds`, Xray не упадет при запуске, но трафик этого юзера "улетит в никуда". Поэтому утилиты `userlist` и `newuser` перед включением WARP проверяют наличие канала через `xray_migrate`.
